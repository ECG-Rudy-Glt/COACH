## [Unreleased]
### Added
- Current level estimated from recent data (C14, C15): when only a personal best is entered, the trajectory and the quality-session paces now use the best run of the last 8 weeks measured by the watch (converted with Riegel, C10) instead of the record. A sustained effort (average HR ≥ 85 % of max HR) gives an estimate, otherwise it is shown as a bound (*at least as fast as*); easy runs, short outings and hilly outings are ignored. Priority: current time entered > watch > record only. The trajectory API exposes `level.source_kind` (`saisi` | `garmin` | `record`), `level.bound` and `level.source_date`, and the AI coach receives the source type.
- *My performances*: for the reference lifts, the current level estimated from logged sets (Epley e1RM, 1 to 10 reps, last 12 weeks) is shown as *estimated* with its date; it never replaces the user's entry and now seeds the suggested starting load when no current level was entered. Cycling and other sports are not estimated yet (the watch import has no power data).
- Statistics screen, *Consistency* section: goal of the week, weekly streak (weeks with at least 75 % of the planned sessions done; skipped sessions and empty weeks never break it), last 12 weeks. No badges, no reminders; can be turned off in *Profile* (`GET/PUT /users/{id}/stats/preferences`, no migration). Rules ST11 to ST13.
- Statistics screen, *Progress* section: 5 km and 10 km records (declared, measured by the watch, watch estimate, kept apart), lift records and per-exercise curves with an estimated 1RM (≈), trajectory towards the performance goal (C10 to C12) with the watch's estimates, weekly volume over 12 weeks and pace per run (rules ST6 to ST10).
- English version of the whole app (issues #21, #22, #23), French stays the default: interface, questionnaire and *My performances* page, plan / nutrition / advice texts, error messages, push notifications and weekly e-mail, and the AI coach (per-language prompts in `data/prompts/`, explicit answer-language rule on every LLM call, meal estimates included). Language selector on the login screen and in *Profile*; the choice is kept on the device and on the account (`users.lang`, `PUT /auth/language`, migration 0013); `GET /bank?lang=`, `X-Lang` header, `Accept-Language` and the `LOCALE` variable select the language of a request. One dictionary (`app/static/i18n/en.json`, French text as key) is shared by the browser and the server. See `docs/i18n.md` and the updated `skills/add-language`; `scripts/i18n_check.py` and `tests/test_i18n.py` fail when a text, a question, a prompt or a notification is left untranslated.
- Statistics screen (daily): steps per day, estimated calories and protein over 7 days against the target (shown with ≈), weight with its 7-day trend, this week's sessions and recent activities, all computed by the engine from stored data; every chart has a text table. The Garmin sync now also fetches daily steps (rules ST1 to ST5).
- Meal estimates, clarifying questions (N9): when the estimate is not confident, the model may ask 1 or 2 short questions (portion, cooking fat, sauce, drink) with quick-answer buttons; the estimate is redone with the answers, or kept as is with *Skip*. The server caps the number and length of questions and never asks again after answers; the form has an opt-out.
- Meal form: barcode for packaged food (N10) — type the code or scan it where the browser supports `BarcodeDetector`; per-100 g values from Open Food Facts × the quantity eaten, no AI call. Only the code leaves the server (explicit user agent, 6 s timeout); `OFF_ENABLED=0` turns it off, `OFF_BASE_URL` points to a mirror.
- Meal correction: edit kcal and macros of any meal; the corrected figures win, and recent corrections and identical past descriptions are given as examples to later estimates of the same user (no identity).
- Nutrition screen: the 7-day average of estimated days is the main figure, the day and single meals come second (N6). Tests use recorded provider replies for the meal JSON schema (#34, #55).
- Plan screen: *Table* view of the week, one column per day like a kanban board; long-press a card then drag it to another day (touch on iPhone and Android, mouse on desktop; the board scrolls by itself near the edges). The choice of view is remembered.
- Interactive onboarding: welcome screen, 13 essential questions, a loading page while the coach AI reads the profile, then either the app or *Your coach asks* (missing questions chosen by the model among the bank, validated and bounded by the server, with a rule-based fallback and free-text clarifications). First plan generated at the end. See `docs/onboarding.md`.
- Profile page: the answered questions are grouped in collapsible sections.
- Garmin matching: activities are linked to sessions logged by hand as well as planned ones (same day, same sport, closest duration), every time the plan opens and after each sync; the old matcher was only used by tests. Off-plan activities can be linked manually to a session (the session then moves to the day it was really done), and unlinked again.
- Reschedule a session: *Change day* on the session screen (bottom sheet, any date in range) or long-press then drag the session onto a day (touch on iPhone and Android, mouse on desktop). Non-blocking warnings for two hard sessions within 48 h or legs next to a key run (G5, I1, I2); the original day is kept (`moved_from`).
- Long-horizon trajectory for dated *performance* goals (e.g. 10 km under 40 min in two years): current level from race records (C10), base → threshold → specific → taper phases with timed checkpoints every 3 months (C11), and a weekly-volume target instead of an unbounded build (C12). Exposed as `trajectory` on `GET /users/{id}/plan`, shown in the plan screen and given to the coach.
- Threshold and goal-pace quality sessions during those phases; an undated or conflicting ultra is reported instead of silently ignored.
- Meal form: *Lunchbox for tomorrow* — a meal prepared (and estimated) the evening before is saved on tomorrow's lunch, so its calories count on the day it is eaten; the day arrows now reach tomorrow.
- Dedicated CrossFit programming (rules M10, M14 to M17): without running declared, a week of 2 to 6 distinct sessions according to the available days — lower-body strength, metcon (AMRAP, For Time, EMOM or intervals, a different format each week), gymnastics and upper-body strength with regressions by level, aerobic capacity in zone 2, upper-body strength with light technical weightlifting, a second capacity metcon or prevention. Never two hard days in a row on the same muscle groups, 4-week progression and lighter week, moves replaced when an injury is declared.
- Dedicated Hyrox programming (rules M18 to M21): quality run (1 km repeats at Hyrox pace, threshold), station sessions with the official loads of the chosen category (Open or Pro, men or women, reached progressively), compromised running (station then 1 km), upper-body support and low-impact aerobic work; run volume follows G1 to G3. With a dated Hyrox goal: half simulation 5 weeks out, one full simulation 3 weeks out, taper, nothing hard the day before or the two days after. Without a goal: a half simulation every 8 weeks.
- Running + Hyrox or CrossFit (rule I7): the long run and the quality run stay, one hard hybrid session per week at most (stations and compromised running alternate), its running counted in the weekly run volume, the full simulation replaces the long run; a run goal within 8 weeks still wins (CrossFit disappears, Hyrox keeps one light stations session).
- Evidence base: 11 publications on Hyrox, CrossFit and high-intensity functional training (HYB-004 to HYB-014), with their limits and the gaps (no trial of a complete programme, nothing on compromised running or simulation frequency).
- English translations of the new session titles, notes and instructions.
### Changed
- Hybrid sessions count 6 MET in the energy target (instead of the 4 MET default); a Hyrox goal title containing "Hyrox" no longer reads its 8 km as a running goal; a declared tibia injury now also removes jumping moves.
- Meal estimates: a weight given in the description is multiplied by typical cooked-dish densities (a 430 g stew is ~700 kcal, not 380); the prompt now asks for the high end of the range for big plates (sauces, cooking fat, restaurant portions) and the per-meal ceiling is raised from 2,500 to 3,500 kcal; estimates were clipped and too low.
- Meal photo: two large buttons (*Take a photo* opens the camera directly on iPhone and Android, *Photo library*), preview with a remove button, and tips for a better estimate. `[hidden]` now always hides an element (the chat suggestion chips did not disappear while typing).
- LLM providers: per-provider JSON mode (`json_mode` in `data/llm_providers.yaml`, `LLM_JSON_MODE` override) for the weekly review, notifications and meal estimates, and a graceful fallback without tool calling (`LLM_TOOLS`, catalog `tools` flag, or a server that refuses the option). Adapter tests use sample provider responses (`tests/fixtures/llm`).
- `app/repo.py` (880 lines) split into the `app/repo/` package, one module per domain behind the same `Repo` protocol; `from app.repo import MemoryRepo, PostgresRepo, Repo` keeps working. No SQL or behaviour change (method sources are identical, PostgreSQL tests pass).
- Plan screen: the cycle, objective, trajectory and coach-review cards at the top are collapsible (title and one-line summary stay visible, the state is remembered per card; the coach review opens by itself when a proposal or a question is waiting).
- Coach chat: typing indicator, animated bubbles, composer pinned above the tab bar with an auto-growing field and a round send button (Enter sends on desktop), suggestion chips, and an inline *Retry* instead of a lost message.
- Release process documented in `docs/releasing.md`; a CI check requires a `CHANGELOG.md` entry when code, migrations, questions or rule data change.
- CI reports test coverage (job summary) and fails below a minimum threshold (`.coveragerc`, currently 83 %).
- Background jobs start from a FastAPI lifespan handler instead of the deprecated `on_event` hook (no behaviour change).
### Fixed
- Performance goal: when the level comes only from a personal best (no current time entered), the screen and the coach call it a starting point, likely faster than your current level, instead of "estimated current level" (rule C13).
- The plan no longer schedules sessions on the day of the event (whatever the weekday), keeps the day before short and easy, and leaves 2 days without running after it (rule C6).
- A declared pain on a zone that carries running (knee, ankle, hip, shin, Achilles, calf, foot, hamstring) now freezes running volume, long run and intensity (rule S2); calf, foot and hamstring pain are recognised in session notes.
- Individual exercises can be excluded with the `history.avoid_exercises` fact (name fragments) without treating the whole body zone as injured.
- With no event within reach, the weekly volume no longer keeps growing until the schedule cap.

## [0.1.0] — 2026-10-19 — first public release
### Added
- Rules-based multisport plan engine with cycles/phases, nutrition engine, adaptive questionnaire (97 questions).
- 60 publications (abstract-level summaries, DOI/PMID checked) linked to rule IDs; a full human review is tracked on the issue board; exercise library import (wger + free-exercise-db).
- LLM coach (weekly review, chat with read-only history tools, notifications) behind a **multi-provider layer**: Anthropic, OpenAI, Gemini, Mistral, OpenRouter, Ollama, any OpenAI-compatible server, or none.
- Garmin Connect sync with automatic session matching.
- Docker Compose stack: internal database network, file secrets (`NAME_FILE`), optional HTTPS proxy, backups and local LLM profiles; one-shot exercise import.
- PWA (iPhone/Android), web push / ntfy / e-mail notifications.
### Security
- Dependencies updated to fix known Starlette advisories (FastAPI 0.147, Starlette ≥ 1.3.1); Dependabot now runs monthly and grouped.
- CSP and security headers, same-origin write check, per-account and per-IP login throttling, registration closes after the first account by default, API docs disabled by default, hardened containers.
